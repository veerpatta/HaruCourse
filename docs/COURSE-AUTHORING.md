# Course authoring and acceptance standards

Use [the original brief](../COURSE-VISION-ORIGINAL.md) and [requirements matrix](../COURSE-REQUIREMENTS.md) when designing or changing course content. Explicit later user decisions take precedence; record substantive refinements in the matrix. Do not silently narrow the course or treat app features as educational coverage.

Do not replace instruction with “learn X” or an external tutorial link. Teach enough to start the assignment. Expand craft/tool topics with concrete demonstrations or examples when a short explanation is insufficient. Timeboxes include reading, setup, practice, recording and review—not just tool activity.

## Tool module template

Record category (Essential / Important / Useful / Optional), capability needed, why this tool, transferable concept, target skill level, prerequisites, curriculum placement, lesson path, focused exercises, mini-project, practical test, current plan restrictions and free substitute. Evaluate all tools named in the brief without requiring all of them. Existing Adobe experience may warrant assessment rather than retraining.

## Project brief template

Include the original brief's 21 elements: problem; context; target users; business context; research; competition; synthesis; useful personas/JTBD; journey; IA; flows; wireframes; prototypes; UI; design system; testing; iterations; final solution; impact/metrics; reflection; case-study structure. Explain omissions where a method does not fit. Add participant access, constraints, estimated hours, evidence checkpoints and a reviewer rubric.

Observed results, simulated training data, proposed metrics and production outcomes must have distinct labels. Keep originals and revisions. An unshipped concept cannot claim real conversion/retention improvements. Simulated examples teach a method but never count as real participants.

## Resource and current-awareness records

Prefer primary documentation, then credible industry/educational sources. Verify mutable tool features, pricing and job requirements at authoring time. Keep lasting principles separate from a date-specific workflow. Record why each resource deserves the learner's limited time.

Maintain a small prioritized book list with Must Read, Highly Recommended, Advanced and Reference categories. Required paid reading needs a free route or replacement. A Stay Current plan must specify selected sources, cadence, a time limit and an evidence-quality filter; it must not become mandatory daily scrolling.

## Assessment and tracker contract

The target statuses are Not Started → Learning → Practicing → Completed → Portfolio Ready → Mastered. Current app readiness is a submission state, not Completed. Portfolio Ready applies to artifacts; Mastered requires repeated independent transfer after a delay.

For each assessment, retain lesson/project ID and version, submission revision, date, reviewer, applicable rubric scores, evidence, critical failures, outcome, remediation and reassessment. A score of 2 on every applicable critical dimension is the current proposed pass rule; no primary-task blocker or material exclusion may be ignored. Assign a focused two-to-four-hour repair where appropriate and update the schedule.

Tracker records must eventually cover date, topic, actual time, resource completion, assignment/reference/status, portfolio work, tool skills, confidence, quiz score, feedback and revision needs. Do not treat quiz answers revealed in a lesson as a recorded test score. Do not claim the current app implements the full tracker until these fields and workflow are present.

## Publication checklist

- Map the lesson to a requirement, prerequisite and intended artifact.
- Check the time budget and ensure optional work is not counted as required.
- Verify resource links and cost constraints; date changing facts.
- Check teaching clarity, worked example, assignment feasibility and real-evidence requirements.
- Include understanding checks, practical criteria and a next step.
- Validate stable IDs and record isolation; preserve old submissions when content changes.
- Keep Markdown and app material consistent, and document whether a source or generated copy is authoritative.
- Test the actual learning/submission path when changing the app; local tests and hosted checks are distinct.
- Update progress as authored/published/tested, never as learner completion.
