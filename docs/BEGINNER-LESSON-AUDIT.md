# Beginner learning-gap audit — all published lessons

Dated 7 September 2026. This is the implementation baseline for the next course refinement. It reviews all 224 published teaching lessons in their prerequisite order from the perspective of a learner rebuilding product-design knowledge and with limited technical knowledge. It does not score Haru, claim that she attempted the lessons, or replace observation of her using the course.

## Overall judgment

The curriculum has unusually strong breadth, evidence boundaries and real-work intent. Its main weakness is instructional support: many lessons specify professional-quality work more clearly than they teach a beginner how to produce it. A worked answer inside a disclosure is useful reference, but it is not the same as watching a decision being made, trying one part with feedback and then working independently.

The audit found six recurring gaps:

1. **Demonstration gap.** Lessons commonly move from concise principles to five demanding production steps. Examples often show a finished result rather than the thinking and mistakes that produced it.
2. **Guidance gap.** Only seven of 224 lessons currently carry the refined step/worksheet contract. Large exercises appear at once instead of revealing one manageable decision at a time.
3. **Tool gap.** Several pre-web lessons suggest HTML, CSS, SVG or running prototypes; later lessons introduce developer tools and code without a control-level tour, starter or recovery path.
4. **Access gap.** Research, testing, delivery and project lessons often need participants, a team, an engineer, a live build or real operations. Some fallbacks exist, but they are inconsistent and can make unavailable access feel like failed learning.
5. **Feedback gap.** Check questions reveal answers. They do not first collect the learner's reason, diagnose a misconception or require a repair to the learner's own artefact.
6. **Continuation gap.** Prerequisites are pedagogically sound but fragile when an earlier artefact is missing, weak or created in a different practice context. Saving instructions can conflict between the in-app route and the generic external-file route.

## Course-wide direction

Every refined lesson should use **See it → Try it with help → Try it yourself → Check the reason → Improve your work → Save and continue**. Keep Learn → Do → Check → Your work as the interface sections. “See it” demonstrates a complete reasoning chain. “Try it with help” uses one small supplied case. “Try it yourself” produces the lesson artefact. “Check” requires an answer before feedback. “Improve” changes the learner's artefact. Saving instructions reflect the route actually chosen.

Do not turn every lesson into a long form. Use the smallest number of fields that makes reasoning visible, normally one decision per screen and one complete worked row before repeated rows. Preserve existing worksheet field IDs and saved answers.

## Completion evidence for each row

A lesson leaves this register only when its authoritative source has been reviewed and the following evidence exists:

- The visible teaching supplies every new idea needed for the task or names an earlier lesson where it was practised.
- A complete, labelled example exposes the reasoning, uncertainty and a likely wrong turn.
- The learner gets a small supported attempt before the independent artefact. Help fades rather than disappears abruptly.
- Tool instructions begin from a known screen or provided starter, name exact controls, show the expected result and explain recovery from a common failure.
- A no-access route preserves the competency when a person, team, device, build or service is unavailable. It is labelled practice and never presented as real evidence.
- Check requires a learner response before feedback and sends one specific issue back into the artefact for repair. Formal scoring remains separate.
- Save/review/resume instructions match the chosen route. Existing IDs, records, submissions, feedback and bookmarks remain intact.
- Content generation and checks pass; relevant mobile, keyboard, offline and persistence behaviour is verified in proportion to the change.
- Haru's observed use is recorded separately. Agent completion and creator review are not learner validation.

## Delivery diagnosis — 7 September 2026

The creator's session showed a standing "update available" notice while the old lesson stayed on screen. The cause is in the artefact, not the browser: the built `dist/sw.js` contained no `skipWaiting` and no `message` listener, and `src/main.tsx` discarded the update function that `registerSW` returns. A newly installed worker therefore had no way to be activated from the page. The notice's own advice — close and reopen the app — only works when every window and tab for the origin has closed, which a second open tab quietly prevents. So the learner could keep an older course indefinitely while being told an update existed.

The fix keeps activation with the learner: the worker now answers a `SKIP_WAITING` message, and the notice carries an "Update now" button that first checks for practice drafts still marked unsaved and refuses until they have uploaded. Nothing reloads on its own.

This was verified structurally, not end to end: the built worker now contains the listener and the page renders the button. **A live waiting-to-active swap has not been observed** — the app's browser pane cannot register a service worker at all in this environment, and the separate real-browser tool was disconnected during the session. The creator should confirm the swap once in a real browser, and that check is still open.

## Hidden teaching restored across m03-m07 — 7 September 2026

The adapter that brings the legacy-shape modules into the reader (`adaptPublished` in `src/teaching.ts`) put only the lesson objective in the visible Learn list and moved every authored teaching paragraph into `explanation`, which the reader renders inside a “Why this works” disclosure. Fifty-six lessons across m03 to m07 therefore opened with a single sentence and hid 224 paragraphs of teaching behind a click.

The adapter now puts the authored teaching in the visible path and leaves `explanation` empty so nothing is printed twice, and the reader shows the objective above it as “What you will produce”. The generated Markdown is byte-identical, because the text itself did not change — only where the app shows it. Verified in the browser on m03, m05 and m07: four visible teaching paragraphs, the objective above them, no “Why this works” duplicate, and no overflow at 320 px.

This is a shared repair, not a lesson refinement. Every m03-m07 row still needs its demonstration, supported attempt, active check and guided practice before it can leave this register.
